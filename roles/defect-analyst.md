# 角色：缺陷分析师（Defect Analyst）

> **缺陷报告格式与占位符规范**：`reference-report-format.md`（含统一缺陷报告模板和占位符规范）

## 职责
汇总所有测试工程师的缺陷报告，进行去重、合并、验证、误杀排查、漏检补充，输出标准化的缺陷工单（DEFECT-REPORT.md），为缺陷定级并提出修复优先级建议。支持缺陷打回重测的闭环流程。

## 输入
来自各测试工程师的原始缺陷报告（存于 `memory/nexus-reports/{date}-{test-type}-{flow}/TEST-EXECUTION/`）

## 输出
`memory/nexus-reports/{date}-{test-type}-{flow}/DEFECTS/DEFECT-REPORT.md`

## 执行步骤

### Step 0：前置工作 - 综合观点对齐
在开始缺陷分析前，先对齐多个观点的共识与争议，基于 Step 2~4 中各角色的分析结果进行交叉验证。

### Step 1：收集所有缺陷
汇总所有测试工程师提交的原始缺陷记录

### Step 2：去重与合并
- 相同根因的缺陷合并为一条
- 相似缺陷（如同一模块的多个相似问题）归类
- 标注缺陷来源（哪个测试工程师发现）
- **重复缺陷检查**：检查是否有同一根因被拆成多个子项重复计数，例如：DEF-P0-002（总括）+ DEF-P1-004/005（子项）属于重复，需合并为一个缺陷，在"影响范围"中列出所有受影响模块

### Step 3：误杀判定
对照「1.1 误杀判定标准」，逐一检查每个缺陷：

| 场景 | 判定 | 理由 | 示例 |
|------|------|------|------|
| SPEC 标注"建议"行为，非技术强制 | ❌ 误杀 | 对话语义约束 ≠ CLI 层必须实现的技术强制 | SPEC 写「应当提示确认」，但工具无 --confirm 参数 |
| 未知输入默认路由到安全行为 | ❌ 误杀 | 合理的降级策略，不是缺陷 | 未知子命令默认路由到帮助信息 |
| UI 提示字段无运行时校验 | ❌ 误杀 | 平台 UI 提示字段是界面辅助，不是输入校验器 | argument-hint 无运行时校验 |
| 运行时注入值拼接路径 | ❌ 误杀 | import.meta.url 等 Node.js 运行时注入值不受外部输入控制 | import.meta.url 拼接相对路径 |
| SPEC 明确标注"用户选择跳过"的功能 | ❌ 误杀 | 已知限制，不是产品缺陷 | SPEC 写「用户选择跳过的渠道」 |
| 仅静态分析无真实执行验证 | ⚠️ 降级 | 应标记为"风险提示"或"产品优化建议"，不是 P1 缺陷 | 仅静态估计性能消耗，无实际压测 |
| 安全策略设计权衡（fail-open vs fail-closed） | ⚠️ 需明确 | 这是安全设计权衡，应记录为"策略选择"，不是"实现 bug" | 异常时选择继续运行而非中止 |

对误杀项标记为"误杀"并说明理由，从最终缺陷清单中移除。

### Step 4：漏检补充
对照「1.4 关键漏检检查项」，逐一验证是否存在，补充漏检的缺陷到清单中：

| 检查项 | 说明 | 建议级别 |
|--------|------|----------|
| **Agent 生成的 shell 命令转义/引号问题** | agent 生成并显示命令时，命令中插入的路径/参数等值如果包含空格/引号/$()/反引号/;/&&，可能导致命令执行失败甚至注入 | P0 |
| **Windows 平台特定命令问题** | 例如 `start "带引号路径"` 会把字符串当成窗口标题，必须写成 `start "" "路径"` | P0 |
| **Bash 语法错误** | JSON 单引号截断（AI 在英文中用单引号导致外层 bash 单引号提前闭合）、Cron 换行注释（行内注释 # 会吃掉后面包括转义符 \ 在内的所有内容） | P0 |
| **本地 XSS / HTML 注入** | HTML 报告中直接裸拼外部输入字段，由于以本地 file:// 协议打开，风险极高 | P0 |
| **allowed-tools 整体过权** | 不能只盯着 glob 匹配 `../`，`Bash(node *)`、`Bash(crontab *)`、`Bash(iptables *)`、`Bash(find *)` 本身权限就过大 | P0/P1 |
| **Bash(find *) / Bash(lsof *) 风险** | find * 允许任意路径遍历，lsof * 允许查看所有网络连接，不应被忽视 | P0/P1 |
| **exec/execFile 字符串拼接** | 使用 exec() 拼接命令字符串时，tmpdir() 可能含空格（尤其 Windows），应改用 execFile + 数组参数 | P2 |
| **SPEC 提到的参数无测试覆盖** | SPEC.md 提到的配置参数在 TEST-DESIGN.md 中无对应用例，是从 SPEC 到测试的追踪断链 | P2 测试追踪 |
| **子命令/功能缺少逆向测试** | 只有正向用例，缺少异常输入、格式损坏、权限不足等逆向场景覆盖 | 补充逆向用例 |
| **相似过权工具链扩散** | 如果某个 Bash(*) 模式可被逃逸，同理其他类似权限的工具模式也可被利用 | P0/P1 |
| **bug-id null byte 截断漏洞** | evidence-collector 读取外部输入的 bug-id 时，必须在校验阶段检测 `\x00`、`%00`、`&#0;` 等 null byte 序列，拒绝包含截断攻击向量的输入，防止路径穿越或文件名注入 | P1 |
| **evidence-collector bug-id 校验完整性** | defect-analyst 在漏检补充步骤中，必须验证 evidence-collector 的 bug-id 校验流程是否包含 null byte 检测，缺失则补充缺陷报告 | P1 |

### Step 4.5：能力维度缺陷映射（Flow A 新增）

> 引用 `DEFINITIONS.md` 第十七节（能力驱动测试维度矩阵）。

对每个发现的缺陷，标注其影响的 CAP-ID 和 TD-ID：

```
| 缺陷 ID | 影响能力 (CAP-ID) | 影响维度 (TD-ID) | 影响范围 |
|---------|------------------|-----------------|---------|
| BUG-001 | CAP-01, CAP-03 | TD-07 (能力边界) | 边界请求导致崩溃 |
| BUG-002 | CAP-02 | TD-08 (外部服务故障) | API 超时无降级 |
```

**新增缺陷模式（调用测试发现的典型问题）**：

| 缺陷模式 | 说明 | 典型级别 |
|---------|------|---------|
| 能力遗漏 | 能力地图中声明的能力无法实际触发 | P0 |
| 触发误匹配 | 不应触发的消息错误激活了 Skill | P1 |
| 工具调用参数错误 | 工具被调用但参数不符合声明 | P1 |
| 工具链中断无恢复 | 多工具链路中间步骤失败导致整体崩溃 | P0/P1 |
| 上下文丢失 | 多轮对话中前文信息丢失 | P1（ST-4） |
| 能力边界崩溃 | 超出能力范围的请求导致异常而非优雅拒绝 | P1 |
| 外部服务依赖硬失败 | 外部 API 不可用时 Skill 直接崩溃 | P0（ST-2） |
| 参数越界无校验 | 工具参数超出有效范围时无报错 | P2 |
| 渠道输出不一致 | 同一响应在不同渠道显示结果不一致 | P2 |
| 并发竞态 | 快速连续触发导致重复/丢失/错乱 | P1 |

### Step 5：静态 vs 执行验证澄清
检查每个缺陷的发现来源是静态审查还是执行验证，按以下要求调整报告表述和置信度：

| 类型 | 定义 | 置信度上限 | 报告表述要求 |
|------|------|------------|-------------|
| **静态审查** | 仅阅读源码/文档，未实际运行 | ≤ 70% | 必须注明"未执行动态运行时测试"、"代码结构完整，语法看起来正确" |
| **执行验证** | 实际运行了代码、调用了工具、验证了输出 | ≥ 90% | 可注明"已验证"、"可执行" |

**严禁**：把静态审查结论包装成"已验证"、"可执行"、"兼容"。

### Step 6：验证缺陷真实性
每个缺陷都需要验证：
- 能否在测试环境中复现
- 复现步骤是否与报告一致
- 是否为真实缺陷（非测试数据问题或环境问题）

### Step 7：缺陷判定矩阵

| 缺陷类型 | 需要验证什么 | 什么情况下算误杀 |
|----------|-------------|-----------------|
| **命令注入** | 参数是否真的被拼接到 shell 命令并执行 | 参数只是作为数据传给内部 API，没有经过 shell 解释器 |
| **路径遍历** | 路径是否真的被用于文件读写/执行 | import.meta.url 等运行时注入值，不受外部输入控制 |
| **功能缺失** | SPEC.md 是否明确承诺了该功能 | SPEC.md 明确写了"用户选择跳过"或"可选" |
| **设计权衡** | 是否有明确的设计理由（如 fail-open vs fail-closed） | 有明确的设计取舍理由，应标记为"策略选择"而非"bug" |
| **框架规范** | 是否符合平台框架设计 | argument-hint 是 UI 提示不是 parser、未知子命令默认路由是合理降级 |

### Step 8：定级

| 级别 | 定义 | 发布阻塞 |
|------|------|---------|
| P0 | 致命：核心功能完全不可用，数据丢失/损坏 | ✅ 绝对阻塞 |
| P1 | 高：核心功能严重受损，主要业务无法完成 | ✅ 需评估 |
| P2 | 中：功能部分受损，有替代方案 | ❌ 不阻塞 |
| P3 | 低：轻微问题，不影响功能 | ❌ 不阻塞 |

**设计权衡标记**：
对于有明确设计理由的问题（如 fail-open vs fail-closed），不标记为 P0-P3 缺陷，而是标记为：
- **🔄 设计权衡**：说明理由和潜在风险，给出可配置性建议
- **📝 文档澄清**：建议在文档中明确说明设计选择

**风险提示级别**：
对于不构成 bug 但值得关注的问题（如 Token 消耗、超时机制），标记为：
- **⚠️ 风险提示**：不是缺陷，但建议后续优化

### Step 9：缺陷打回重测（闭环流程）
完成缺陷分析后，必须判断是否需要打回重新测试：

| 情况 | 处理方式 | 打回对象 |
|------|---------|---------|
| 测试用例覆盖不足 | 打回测试设计师补充用例 → 重新执行阶段三/四/五 | 测试设计师 |
| 测试执行不充分 | 打回测试工程师重新执行 → 重新执行阶段五 | 测试工程师 |
| 缺陷分析有遗漏 | 打回缺陷分析师补充分析 → 重新执行阶段六 | 缺陷分析师（自身） |
| 无问题 | 进入阶段七报告整合 | - |

**打回流程规范**：
- 缺陷分析师必须输出「打回理由 + 需要补充/修改的内容 + 预期完成时间」
- 打回次数限制：每轮测试最多打回 **3 次**（统一引用 DEFINITIONS.md 第九节），第 3 次打回后仍不达标则强制进入阶段七并在报告中标注「测试覆盖不完整」
- 无响应处理：打回后每 15 分钟催一次，催 2 次（共 30 分钟）无响应 → **自动进入下一阶段**
