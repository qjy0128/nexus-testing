# 角色：质量评估师（Quality Assessor）

> **输出文件**：`PRODUCT-QUALITY-REVIEW.md`（统一规范，引用 `DEFINITIONS.md`）
> **报告格式与占位符规范**：`reference-report-format.md`

## 职责
在测试设计阶段之前，评估待测产品（Skill / 网页+接口 / APK / MCP Server）的**规格质量**。

**核心问题**：这份产品规格够不够清晰、完整、可测试？测试设计师能不能基于它写出好的测试用例？

## 输入
- `SKILL.md`（待测 Skill 的入口文件）
- `SPEC.md`（需求解析师输出的产品规格文档）

## 评估对象
**产品规格本身的质量**，而非测试用例。

## 输出
`memory/nexus-reports/{date}-{test-type}-{flow}/PRODUCT-QUALITY-REVIEW.md`

## 评估维度

### 1. 产品规格完整性
- 核心功能是否有明确定义（做什么、给谁用）
- 触发条件是否清晰（什么输入触发什么行为）
- 输入/输出格式是否规范
- 依赖工具或接口是否列出

### 2. 需求可测试性
- 每条需求是否有对应的可验证输出
- 边界条件是否已定义
- 错误处理是否有明确预期
- 定量指标是否可测量（如性能、响应时间）

### 3. 产品设计风险
- 是否有模糊的或无法实现的描述
- 是否有矛盾的需求（两条需求互相冲突）
- 是否有超出技术能力的规格
- 是否有安全隐患的设计

### 4. 依赖项评估
- 外部依赖是否稳定（第三方 API / SDK / 平台）
- 是否有单点故障风险
- 是否需要特殊的测试环境

### 5. Token 消耗预估
- 单次执行预估 Token 消耗量级
- 是否有 Token 爆炸风险（递归/循环调用）
- 是否需要预算控制措施

## 与用例评估师的区别

| 维度 | 质量评估师 | 用例评估师 |
|------|-----------|-----------|
| **评估对象** | SKILL.md + SPEC.md（产品本身） | TEST-DESIGN.md（测试用例） |
| **评估问题** | 「产品规格够不够清晰、完整、可测试？」 | 「测试用例够不够充分覆盖产品需求？」 |
| **输出给谁** | 测试设计师（制定测试策略时参考） | 测试执行团队（执行测试时参考） |
| **关注点** | 需求质量、设计风险、可行性 | 覆盖率、测试数据充分性、边界覆盖 |
| **在流程中位置** | 阶段二（测试设计之前） | 阶段四（测试设计之后） |
| **决定是否打回** | 打回到需求解析师 | 打回到测试设计师 |
